### Advantages of named ACL config mode

* What happens if you delete an individual entry using traditional method when configuring numbered ACL?
  ![ 500](../_assets/Pasted%20image%2020260705191915.png)
  
  Even though we intended to just delete the ACL entry, the entire ACL has been deleted!

* When configuring/editing numbered ACLs from global config mode, <u>you can't delete individual entries, you can only delete the entire ACL!</u>

Luckily, you can delete them individually inside named ACL config mode.

**Advantages of named ACL config mode:**

* You can easily delete individual entries in the ACL with **no** *entry-number*.
  ![ 500](../_assets/Pasted%20image%2020260705191739.png)
* You can insert new entries in between other entries by specifying the sequence number.
  ![ 500](../_assets/Pasted%20image%2020260705192513.png)

### Resequencing ACLs

* There is a *resequencing* function that helps edit ACLs.

* The command is **`ip access-list resequence *acl-id* *starting-seq-num* *increment*`**
  ![Pasted image 20260705193534.png](../_assets/Pasted%20image%2020260705193534.png)
  
  Why is it a bad idea to use increment of 1 when sequencing ACLs? Sometimes we have to add new entries in between already configured entries. Using an increment of 1 will not allow us to insert the newly added entry in the middle of configured entries.

### Extended ACLs

* Extended ACLs function mostly the same as standard ACLs.
* They can be numbered or named, just like standard ACLs.
  - Numbered ACLs use the following ranges: 100 - 199, 2000 - 2699
* They are processed from top to bottom, just like standard ACLs.
* However, they can match traffic based on more parameters, so they are more precise (and more complex) than standard ACLs.
* We will focus on matching based on these main parameters: **Layer 4 protocol/port**, **source address**, and **destination address**.

### Matching based on Protocol

![ 500](../_assets/Pasted%20image%2020260705194458.png)

* **`ip access-list extended *name*`**: the command to enter extended named ACL config mode.
* Using `?` keyword, you can see the protocols you can use to configure in extended ACL.
  - You can use **protocol number** (0 - 255), where the values are the same as in the **Protocol** field of **IPv4** header. For example, OSPF use value of 89, 88 for EIGRP, 6 for TCP, 17 for UDP, etc.
  - Or you can use the **protocol keyword** (eg. ahp, eigrp, ospf, etc.)
* We will focus more on **tcp**, **udp**, and **ip** protocol in this lesson.
* **ip** protocol keyword works like a wildcard. If you use this option, it matches all IP packets. We use it if we don't care about protocol and we just want to permit or deny all packets.

---

### Matching the source/destination IP address

![ 500](../_assets/Pasted%20image%2020260705195322.png)

* Using `deny tcp ?`, any packet with a TCP segment inside will match this part of the entry.
* We still have to enter the source or destination address to make the entry.
* In extended ACLs, to specify a /32 source or destination you have to use the **host** option or specify the wildcard mask. You can't just write the address without either of those.

![ 500](../_assets/Pasted%20image%2020260705201510.png)

* We specified `any` to match any source host address.
* We can either specify the **destination address**, **any**, or **host** as destination.

![ 500](../_assets/Pasted%20image%2020260705201727.png)

* We decided to use `10.0.0.0` as destination address, and use /24 netmask which is equivalent to `0.0.0.255` as wildcard mask.
* Based on the entry configured, it will **deny all packets that encapsulate a TCP segment, from any source, to destination `10.0.0.0/24`**.

### Extended ACL entry practice (1)

1. **Allow all traffic**
   --> **`R1(config-ext-nacl)# permit ip any any`**

1. **Prevent `10.0.0.0/16` from sending UDP traffic to `192.168.1.1/32`**
   --> **`R1(config-ext-nacl)# deny udp 10.0.0.0 0.0.255.255 host 192.168.1.1`**

1. **Prevent `172.16.1.1/32` from pinging hosts in `192.168.0.0/24`**
   --> **`R1(config-ext-nacl)# deny icmp host 172.16.1.1 192.168.0.0 0.0.0.255`**

### Matching the TCP/UDP port numbers

* When matching TCP/UDP, you can optionally specify the source and/or destination port numbers to match.
  
  ![ 500](../_assets/Pasted%20image%2020260705203320.png)

![ 300](../_assets/Pasted%20image%2020260705203608.png)

You can either use port number or the keyword to match, but it is better if you know the port number of the protocol you want to filter traffic on.

![ 500](../_assets/Pasted%20image%2020260705203720.png)

This command **deny all packets destined for IP address 1.1.1.1/32, TCP port 80**, which means all HTTP segments reaching the mentioned address will be blocked.

After the destination IP address and/or destination port numbers, there are many more options you can use to match (not necessary for the CCNA). Some examples:

* **ack:** match the TCP ACK flag
* **fin:** match the TCP FIN flag
* **syn:** match the TCP SYN flag
* **ttl:** match packets with a specific TTL value
* **dscp:** match packets with a specific DSCP value

If you specify the protocol, source IP, source port, destination IP, destination port, etc, a packet must match ALL of those values to match the ACL entry. Even if it matches all except one of the parameters, the packet won't match that entry of the ACL.

---

### Extended ACL entry practice (2)

1. **Allow traffic from `10.0.0.0/16` to access the server at `2.2.2.2/32` using HTTPS**
   --> **`R1(config-ext-nacl)# permit tcp 10.0.0.0 0.0.255.255 2.2.2.2 0.0.0.0 eq 443`**

1. **Prevent all hosts using source UDP port numbers from 20000 to 30000 from accessing the server at `3.3.3.3/32`**
   --> **`R1(config-ext-nacl)# deny udp any range 20000 30000 host 3.3.3.3`**

1. **Allow hosts in `172.16.1.0/24` using a TCP source port greater than 9999 to access all TCP ports on server `4.4.4.4/32` except port 23.**
   --> **`R1(config-ext-nacl)# permit tcp 172.16.1.0 0.0.0.255 gt 9999 host 4.4.4.4 neq 23`**

### Extended ACL example

![Pasted image 20260705205800.png](../_assets/Pasted%20image%2020260705205800.png)

Let's use the same kind of network again but this time for demonstrating extended ACLs.

**Requirements:**

* Hosts in `192.168.1.0/24` can't use HTTPS to access SRV1.
* Hosts in `192.168.2.0/24` can't access `10.0.2.0/24`.
* None of the hosts in `192.168.1.0/24` or `192.168.2.0/24` can ping `10.0.1.0/24` or `10.0.2.0/24`.

#### Requirement \#1

![697](../_assets/Pasted%20image%2020260705210401.png)

* After configuring the main filter, we used `permit ip any any` to allow all traffic if none of the traffic matches the previous entries.
* Now where to place this ACL? Should we apply it as close to the destination as possible? No.
* **Extended ACLs should be applied as close to the <u><b>source</b></u> as possible, to limit how far the packets travel in the network before being denied.**
* Standard ACLs are less specific, so if they are applied close to the source there is a risk of blocking more traffic than intended.

Now where to apply the ACL? We should apply it **inbound** to R1's G0/1 interface.

![Pasted image 20260705211017.png](../_assets/Pasted%20image%2020260705211017.png)

If PC1 tries to access SRV1 using HTTPs, the packet will be dropped right away if it reaches R1.

#### Requirement \#2

![Pasted image 20260705211411.png](../_assets/Pasted%20image%2020260705211411.png)

* We applied the ACL as close to the subnet as possible, which is R1's G0/2 interface.

#### Requirement \#3

![Pasted image 20260705212055.png](../_assets/Pasted%20image%2020260705212055.png)

* We don't have to block ICMP packets from `192.168.2.0/24` to `10.0.2.0/24` because we already configured it in requirement #2.
* We placed the ACL **outbound** on R1's G0/0 interface, since all packets from the source subnets will travel out of this interface before reaching SRV1 or SRV2.

Here is the ACLs we configured using `show access-lists` command.

![ 500](../_assets/Pasted%20image%2020260705212242.png)

This is not the most elegant solution, you can probably make a more efficient ACLs while having fewer entries. But the one we configured fits all the requirements anyway.

![ 500](../_assets/Pasted%20image%2020260705212453.png)

You can also check which ACLs are applied on the interface. One more use case of **`show ip interface *interface-id*`** is you can see which access list is inbound and which access list is outbound on that interface.
