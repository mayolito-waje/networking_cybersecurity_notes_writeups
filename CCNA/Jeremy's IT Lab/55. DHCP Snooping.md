### DHCP Snooping

* DHCP snooping is a security feature of switches that is used to filter DHCP messages received on *untrusted* ports.
* DHCP snooping only filters DHCP messages. Non-DHCP messages aren't affected
* All ports are *untrusted* by default.
  - Usually, **uplink** ports are configured as *trusted* ports, and **downlink** ports remain *untrusted*.
  - ![ 500](../_assets/Pasted%20image%2020261004192819.png)
  - **Downlink ports** are ports pointing toward the end hosts. **Uplink ports** are ports pointing toward the DHCP server or relay agent and away from the end hosts.

**DHCP Snooping Example:**

![ 500](../_assets/Pasted%20image%2020261004193118.png)

* If PC1 sends a DHCP message, and it reached SW1's *untrusted port*, the DHCP message will be checked. This is why you set downlink ports (ports pointing toward the end host(s)) as *untrusted*. Never trust DHCP messages from end hosts.
* The DHCP server or relay agent will sent a DHCP message as a reply. But since it passes *trusted* ports, the DHCP message will not be checked and will safely reach the end hosts.

![ 500](../_assets/Pasted%20image%2020261004193537.png)

* Untrusted ports can also discard DHCP messages sent by end hosts. There are cases why a DHCP message will be rejected. Perhaps PC2 is trying to use a DHCP exploit, so the message is discarded by SW1.

### Common Type of DHCP Attacks

#### DHCP Starvation

![ 500](../_assets/Pasted%20image%2020261004193943.png)

* An example of DHCP-based attack is **DHCP starvation** attack.
* An attacker uses *spoofed* MAC addresses to flood DHCP Discover messages.
* The target server's DHCP pool becomes full, resulting in a denial-of-service to other devices.
* **CHADDR (Client Hardware Address)**: Recall that in a life of a packet, the source MAC address is always changed (encapsulation and decapsulation of Ethernet frame) whenever a packet reaches the next hop (a router). A DHCP relay agent might use its own MAC address as a source MAC to reach the next hop, so CHADDR field is used to store the original sender's MAC address.

#### DHCP Poisoning

![ 500](../_assets/Pasted%20image%2020261004194807.png)

![ 500](../_assets/Pasted%20image%2020261004194905.png)

![ 500](../_assets/Pasted%20image%2020261004194957.png)

* Similar to ARP Poisoning, DHCP Poisoning can be used to perform a Man-in-the-Middle (MitM) attack.
* A *spurious* (illegitimate) DHCP server replies to clients' DHCP Discover messages and assigns them IP addresses, but makes the client use the spurious server's IP as the default gateway.
  \*==Clients usually accept the first OFFER message they receive==. So if the DHCP server is a remote server and R1 is just a relay agent, the spurious server's DHCP Offer will reach the client first.
* This will cause the client to send traffic to the attacker instead of the legitimate default gateway.
* The attacker can then examine/modify the traffic before forwarding it to the legitimate default gateway.
* **NOTE:** If the legitimate DHCP server's DHCP Offer reaches the client but the client already accepted another DHCP Offer, it will send a DHCP Decline to the DHCP server.

![ 500](../_assets/Pasted%20image%2020261004195706.png)

* If PC1 wants to communicate to the Internet, the Spurious DHCP Server can intercept traffic before it sends it to the Internet. PC1 will be unaware that its sent traffic is being intercepted.

### DHCP Messages Review

* When DHCP Snooping filters messages, it differentiates between **DHCP Server** messages and **DHCP Client** messages.
* Messages sent by **DHCP Servers:**
  - OFFER
  - ACK
  - NAK = Opposite of ACK, used to decline a client's REQUEST
* Messages sent by **DHCP Clients:**
  - DISCOVER
  - REQUEST
  - RELEASE = Used to tell the server that the client no longer needs its IP address
  - DECLINE = Used to decline the IP address offered by a DHCP server

---

### DHCP Snooping Operations

* If a DHCP message is received on a **trusted port**, forward it as normal without inspection.
* If a DHCP message is received on an **untrusted port**, inspect it and act as follows:
  - If it is a **DHCP Server** message, discard it.
  - If it is a **DHCP Client** message, perform the following checks:
  DISCOVER/REQUEST messages: Check if the frame's source MAC address and the DHCP message's CHADDR fields match. Match = forward, mismatch = discard
  RELEASE/DECLINE messages: Check if the packet's source IP address and the receiving interface match the entry in the *DHCP Snooping Binding Table*. Match = forward, mismatch = discard
* When a client successfully leases an IP address from a server, create a new entry in the *DHCP Snooping Binding Table*.

### DHCP Snooping Configuration

![Pasted image 20261004201234.png](../_assets/Pasted%20image%2020261004201234.png)

* We need to enable DHCP snooping globally (`ip dhcp snooping`) and also enable it on VLANs if necessary (`ip dhcp vlan *vlan*`)
* By DEFAULT, all ports will be *untrusted*. We have to manually specify which ports to trust (`ip dhcp snooping trust` in interface configuration mode).
* SW2's G0/0 is connected to R1 so we trusted it. SW1's G0/0 is pointing toward R1 so it should also be trusted.
* `show ip dhcp snooping binding` = show DHCP snooping table. RELEASE/DECLINE messages will be checked to make sure their IP address/interface ID match the entry in the DHCP snooping table. If not matched, the message will be discarded.
  - This prevents attackers from sending these messages on behalf of other devices in the network, causing the DHCP server to believe that they don't need their IP address anymore.

### DHCP Snooping Rate Limiting

![Pasted image 20261004202208.png](../_assets/Pasted%20image%2020261004202208.png)

* DHCP snooping can limit the rate at which DHCP messages are allowed to enter an interface.
* If the rate of DHCP messages crosses the configured limit, the interface is err-disabled.
* Like with Port Security, the interface can be manually re-enabled, or automatically re-enabled with errdisable recovery.
* `ip dhcp snooping limit rate 1` = limit the rate of DHCP messages to *1 DHCP message per second* (this is too low even for legitimate DHCP networks, but is configured in the example to trigger err-disabled state)

![Pasted image 20261004202557.png](../_assets/Pasted%20image%2020261004202557.png)

* `errdisable recovery cause dhcp-rate-limit` = enable ErrDisable Recovery for DHCP Snooping Rate Limiting.
* Rate limiting is very useful against DHCP exhaustion attacks. This is to ensure that malicious DHCP messages will be discarded even if the attacker succesfully manipulated both the source MAC address and the CHADDR to bypass DHCP snooping configurations.

### DHCP Option 82 (Information Option)

![Pasted image 20261004203430.png](../_assets/Pasted%20image%2020261004203430.png)

* Option 82, also known as the 'DHCP relay agent information option' is one of many DHCP options.
* It provides additional information about which DHCP relay agent received the client's message, on which interface, in which VLAN, etc.
* DHCP relay agents can add Option 82 to messages they forward to the remote DHCP server.
* With DHCP snooping enabled, by default Disco switches will add Option 82 to DHCP messages they receive from clients, <u>even if the switch isn't acting as a DHCP relay agent</u>.
* By default, Cisco switches will drop DHCP messages with Option 82 that are received on an untrusted port.

Let's say that `ip dhcp snooping information option` is enabled on both switches.

![Pasted image 20261004203558.png](../_assets/Pasted%20image%2020261004203558.png)

If SW1 receives DISCOVER message on one of it's untrusted ports, it will add Option 82 to the DISCOVER message before forwarding the message to SW2. SW2 will drop the packet after it receives the message on it's G0/1 interface (which is an *untrusted* port).

It will work well if SW2 is a Layer 3 switch acting as a DHCP relay agent. But with network like above, it won't work.

![Pasted image 20261004203941.png](../_assets/Pasted%20image%2020261004203941.png)

What if Option 82 is disabled on SW1 but not disabled on SW2? This time SW1 will not add Option 82 to the DISCOVER message but SW2 will still add Option 82 before forwarding it to R1.

R1 will drop the packet after it receives the DISCOVER message. R1 will drop DHCP messages with Option 82 that are not sent by relay agents (inconsistent relay information).

==**tl;dr:** If the DHCP message was not sent by a relay agent, don't add Option 82 (`no ip dhcp snooping information option`)==
