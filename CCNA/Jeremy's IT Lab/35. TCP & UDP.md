### Functions of Layer 4 (Transport Layer)

![500](../_assets/Pasted%20image%2020260624060129.png)

Some of the functions of Transport Layer are:

* Provides transparent transfer of data between end hosts.
* Provides (or doesn't provide) various services to applications:
  - reliable data transfer
  - error recovery
  - data sequencing
  - flow control
* Provides Layer 4 addressing (**port** numbers, note that the port DOESN'T mean physical interfaces/ports on network devices).
  - identify the Application Layer protocol
  - provides session multiplexing

### TCP Overview

* TCP is **connection-oriented**. Before actually sending data to the destination host, the two hosts communicate to establish a connection. Once the connection is established, the data exchange begins.
* TCP provides reliable communication. The destination host must acknowledge that it received each TCP segment. If a segment isn't acknowledged, it is sent again.
* TCP provides **sequencing**. Sequence numbers in the TCP header allow destination hosts to put segments in the correct order even if they arrive out of order.
* TCP provides. flow control. The destination host can tell the source host to increase/decrease the rate that data is sent.

---

### TCP Header

![Pasted image 20260627134038.png](../_assets/Pasted%20image%2020260627134038.png)

Here is the TCP header. You don't have to memorize the entire header for CCNA, just the important ones:

* **Source port** and **destination port** are both **2 bytes** in length. This means there are available **65,536** available port numbers.
* **Sequence number** and **Acknowledgement number (if ACK set)** provide sequencing and reliable communication.
* TCP have flag bits. Let's focus on **ACK**, **SYN**, and **FIN**. These three flags are used to establish and terminate connections.
* **Window size** filed is used for flow control.

---

### Establishing TCP Connections: 3-way Handshake

![ 500](../_assets/Pasted%20image%2020260627202650.png)

To establish connection using TCP, it uses a mechanism called **3-way handshake**. Let's say PC1 wants to access data on SRV1 using HTTP.

First, it will establish a TCP connection using two flags as mentioned in TCP header: **SYN** (synchronization) and **ACK** (acknowledgement).

![ 500](../_assets/Pasted%20image%2020260627203002.png)

1. **Handshake #1:** PC1 will send a TCP segment to SRV1 with the **SYN** flag set, meaning the SYN bit is set to **1**.
1. **Handshake #2:** SRV1 will reply with a TCP segment with **SYN** and **ACK** flag bit set to **1**.
1. **Handshake #3:** PC1 will send a TCP segment to SRV1 with the **ACK** bit set to **1**.
1. Now the TCP 3-Way handshake is completed and the connection is established. PC1 and SRV1 can now exchange data with each other!

---

### Terminating TCP Connection: 4-way Handshake

![ 500](../_assets/Pasted%20image%2020260627203809.png)

If PC1 decides it no longer needs connection from SRV1, a **4-way Handshake** can be established. The process uses 2 flags to terminate the TCP connection: **FIN** and **ACK**.

![ 500](../_assets/Pasted%20image%2020260627204042.png)

1. **Handshake #1:** PC1 will first send TCP segment to SRV1 with **FIN** flag bit set to **1**.
1. **Handshake #2:** SRV1 will respond with another TCP segment to PC1 where the **ACK** bit is set to 1.
1. **Handshake #3:** SRV1 will then send its own TCP segment with **FIN** flag set to 1 to PC1.
1. **Handshake #4:** PC1 will respond to the segment with another TCP segment with **ACK** bit set to 1.
1. The termination process is now complete!

---

### TCP Sequencing/Acknowledgement

![ 500](../_assets/Pasted%20image%2020260627204713.png)

1. When PC1 sends the 3-Way Handshake SYN message, it sets a random initial sequence number. Let's say the number is set to 10.
1. When PC2 sends SYN-ACK to PC1, it sets its own random initial sequence number (in this case, 50). By setting the acknowledgement field to 11, it acknowledges the SYN it receives from PC1. Why 11? That's because TCP uses something called **forward acknowledgement**. Instead of acknowledging sequence number 10 with Ack field of 10, it tells PC1 the sequence number of the next segment it *expects* to receive.
1. PC1 will then sends the final ACK of the 3-Way handshake. Sequence number is 11. Using forward acknowledgement, it sets the value to 51 in the Ack field.
1. PC2 replies with Seq of 51, then uses forward acknowledgement by setting the value to 12 in Ack field.
1. The exchange continues...

So, in a nutshell:

* Hosts set a random initial sequence number.
* **Forward acknowledgement** is used to indicate the sequence number of the next segment the host expects to receive.

In TCP overview:

 > 
 > TCP provides reliable communication. The destination host must acknowledge that it received each TCP segment. If a segment isn't acknowledged, it is sent again.

So how is TCP segment sent again if the segment isn't acknowledged?

#### TCP Retransmission

![ 500](../_assets/Pasted%20image%2020260627215346.png)

Let's simplify how TCP re-transmission works by only showing one set of sequence and acknowledgement numbers. What if PC1 fails to send segment to SRV1?

![ 500](../_assets/Pasted%20image%2020260627215718.png)

After PC1 waits a certain amount of time with no ACK received, PC1 will resend the segment. This is known as **TCP retransmission**. SRV1 will receive the resent segment and will finally reply with an ACK using forward acknowledgement.

### TCP Flow Control

* Acknowledging every single segment, no matter what size, is inefficient.
* The TCP header's **Window Size** field allows more data to be sent before an acknowledgment is required.

![ 500](../_assets/Pasted%20image%2020260627215924.png)

For example, a host could send 3 segments before an Ack is being sent. In addition, a sliding window is used to dynamically adjust how large the window size should be.

**NOTE:** ***In all of these examples, very simple sequence numbers are used. In real situations, the sequence numbers get much larger and do not increase by 1 with each message. For the CCNA, just understand the concepts and don't worry about the exact numbers.***

### UDP (User Datagram Protocol)

* UDP is **not** connection-oriented.
  - The sending host does not establish a connection with the destination host before sending data. the data is simply sent.
* UDP **does not** provide reliable communication
  - When UDP is used, acknowledgments are not sent for received segments. If a segment is lost, UDP has not mechanism to re-transmit it. Segments are sent 'best-effort'. **Best effort** means it will do its best to send the data, but there will be no guarantee it will reach the destination.
* UDP **does not** provide sequencing.
  - There is no sequence number field in the UDP header. If segments arrive out of order, UDP has no mechanism to put them back in order.
* UDP **does not** provide flow control.
  - UDP has no mechanism like TCP's window size to control the flow of data.

![Pasted image 20260627221725.png](../_assets/Pasted%20image%2020260627221725.png)

Above is the UDP datagram header taken from Wikipedia. It only has 4 fields: **Source port**, **Destination port**, **Length**, and **Checksum**.

* **Source port** and **Destination port** are self explanatory
* **Length** field indicates the length of the segment.
* **Checksum** field so that the receiving end can check for errors.

### TCP/UDP Comparison

![Pasted image 20260627222101.png](../_assets/Pasted%20image%2020260627222101.png)

* TCP provides more features than UDP, but at the cost of additional **overhead**.
* For applications that require reliable communications (for example downloading a file), TCP is preferred.
* For application like real-time and video, UDP is preferred.
* There are some applications that use UDP, but provide reliability etc within the application itself. TFTP is an example, which we will learn later.
* Some applications use both TCP & UDP, depending on the situation.
