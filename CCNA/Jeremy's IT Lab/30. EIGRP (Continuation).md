### EIGRP Metric

![ 500](../_assets/Pasted%20image%2020260614195805.png)

* By default, EIGRP uses **bandwidth** and **delay** to calculate metric.
* Formula: `([K1 * bandwidth + (K2 * bandwidth) / (256 - load) + K3 * delay] * [K5 / (reliability + K4)]) * 256`
* The default 'K' values are K1 = 1, K2 = 0, K3 = 1, K4 = 0, K5 = 0
* You can simplify the formula like this: metric = **bandwidth** + **delay**
* However, the exact calculation is like this: bandwidth of the **slowest link** + the delay of **all links**

![ 500](../_assets/Pasted%20image%2020260614195914.png)

Let's say R1 wants to connect to the subnet of `192.168.4.0/24`. The route via R2 is the best.

![ 500](../_assets/Pasted%20image%2020260614200110.png)

To get the metric of the best path (R2), the bandwidth of the slowest link (boxed in orange) will be added to the delay of all links (boxed in blue).

Since the default value is based on interface's bandwidth, the router don't actually send an ICMP (ping) to get the values!

### EIGRP Terminology

![ 500](../_assets/Pasted%20image%2020260614200402.png)

* **Feasible Distance** = This router's metric value to the route's destination.
  ![ 300](../_assets/Pasted%20image%2020260614200459.png)
* **Reported Distance** (aka Advertised Distance) = The neighbor's metric value to the route's destination.
  ![ 300](../_assets/Pasted%20image%2020260614200647.png)

![ 500](../_assets/Pasted%20image%2020260614200743.png)

Let's focus on the information `via 10.0.12.2 (28672/28416), GigabitEthernet0/0`:

* The first value, `28672`, is the **feasible distance**.
* The second value, `28416`, is the **reported distance**

![Pasted image 20260614201011.png](../_assets/Pasted%20image%2020260614201011.png)

In `show ip eigrp topology`, you can also see the feasible and reported distance of path through R3 (which has higher metric so it was not included in routing table). Highlighted in **yellow** is the **feasible distance** and the highlighted in **violet** is the **reported distance**.

Another terms to remember:

* **Successor** = the route with the lowest metric to the destination (the best route)
  * The route via R2 has the lowest metric so it is the best route, which makes it the successor.
* **Feasible Successor** = an alternate route to the destination (not the best route) <u>which meets the feasibility condition</u>.
  * A route is considered a **feasible successor** if it's **reported distance** is *lower* than the **successor** route's **feasible distance**.

![ 500](../_assets/Pasted%20image%2020260614202223.png)

`28416` is less than `28672`, so the route via R3 is a **feasible successor**. Feasible successors are made as a **loop prevention mechanism**. If a route meets a feasibility requirement, it is guaranteed not to be a loop route.

### EIGRP Unequal-Cost Load-Balancing

![ 500](../_assets/Pasted%20image%2020260614202601.png)

Look at this value:

![ 500](../_assets/Pasted%20image%2020260614202647.png)

This is the default value (1). With a **variance** of **1**, only ECMP load-balancing will be performed. This means that the path's feasible distance must be equal to the successor route to be considered for load balancing (which makes that path also a successor route, you can have multiple successor routes!)

![ 500](../_assets/Pasted%20image%2020260614203037.png)

The feasible distance of path through R2 and the path through R3 are different, so they can't be used for load balancing.

![ 500](../_assets/Pasted%20image%2020260614203143.png)

* From EIGRP config mode, use `variance ?` where ? is the metric variance multiplier.
  * **Variance 2** = **feasible successor** routes with an FD up to 2x the **successor** route's FD can be used to load-balance.
    
    ![ 500](../_assets/Pasted%20image%2020260614203422.png)
    
    `28672 * 2 = 57344`. `30976` is less than `57344`, so the route via R3 can now be used for load-balancing.

* EIGRP will only perform unequal-cost load-balancing over **feasible successor** routes. If a route doesn't meet the feasibility requirement, it will NEVER be selected for load-balancing, regardless of the **variance**.

![Pasted image 20260614203723.png](../_assets/Pasted%20image%2020260614203723.png)

After you use the `variance` command. The route via R3 will now show in the routing table. But since the path via R2 have lower metric, it will be favored and will be used more for sending traffic even when doing load-balancing!
