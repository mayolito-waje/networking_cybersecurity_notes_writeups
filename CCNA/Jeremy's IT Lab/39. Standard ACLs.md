### What are ACLs?

* ACLs (Access Control Lists) have multiple uses. We will focus on ACLs from a security perspective. There are other types of ACLs, but we will focus on security perspective for now.
* ACLs function as a packet filter, instructing the router to permit or discard specific traffic.
* ACLs can filter traffic based on source/destination IP addresses, source/destination Layer 4 ports, etc.

### How ACLs Work

![Pasted image 20260704210143.png](../_assets/Pasted%20image%2020260704210143.png)

You don't make ACLs randomly. You usually make them to achieve a certain requirement. Let's set up some example requirements.

* **REQUIREMENT:**
  - Hosts in `192.168.1.0/24` can access the `10.0.1.0/24` network
  - Hosts in `192.168.2.0/24` cannot access the `10.0.1.0/24` network.
* ACLs are configured globally on the router (global config mode)
* ACLs are an ordered sequence of ACEs (Access Control Entries). For example:
  1. **ACE 1:** if source IP = `192.168.1.0/24`, then permit
  2. **ACE 2:** if source IP = `192.168.2.0/24`, then deny
  3. **ACE 3:** if source IP - any, then permit
* Configuring an ACL in global config mode will not make the ACL take effect.
* The ACL must be applied to an interface.
* ACLs are applied either **inbound** or **outbound**.

#### Why applying ACL inbound or outbound matters?

![Pasted image 20260704211105.png](../_assets/Pasted%20image%2020260704211105.png)

Just simply picking either inbound or outbound doesn't automatically mean that the ACL will succeed. For example, we have a rule that hosts in `192.168.2.0/24` cannot access the `10.0.1.0/24` network.

If we set the ACL on R1's G0/2 interface using **outbound**, PC3 can ping SRV1, which SHOULDN'T happen based on requirements. Why? Since it's outbound, it **will only apply ACLs on traffic exiting the interface**, not on receiving traffic.

If PC3 pings SRV1, PC3 traffic will be ignored by ACL since it is a **receiving** traffic in R1's G0/2 interface. The packet will reach SRV1 and SRV1 will reply with ICMP. The ICMP reply will have a source address of `10.0.1.0/24`.

Once the ICMP reply reaches R1 again and reach G0/2 interface, this time, the **ACL will take effect** since the traffic will come out of the ACL-applied interface to reach PC3. The source IP address fits the criteria of **ACE 3** (If source IP ANY, then permit), so the ACL will permit reaching PC3, and the ping will succeed (*which shouldn't be*).

![Pasted image 20260704212856.png](../_assets/Pasted%20image%2020260704212856.png)

Now how about using **inbound**? Does this fix the problem? **YES AND NO**.

If PC3 pings SRV1, the packet will have a source IP of `192.168.2.1`. If R1's G0/2 interface receives the traffic, the **ACL will take effect** since the applied ACL is inbound. Look at **ACE 2**: it says that if  source IP comes from `192.168.2.0/24` subnet, then *deny* the traffic.

PC3's IP fits the criteria of ACE 2, so the traffic will be dropped and won't reach SRV1 which will lead to ping error. ACL will ignore other rules once it passes one of the criteria, so rule # 3 will be ignored since ACLs check the ACEs in order. It also fits the ACL requirement of hosts in `192.168.2.0/24` being not able to access the `10.0.1.0/24` network.

But since all traffic from PC3 and PC4 will be denied by R1 due to ACL, the devices won't be able to talk to SRV2. Only access to SRV1 should be denied, PC3 and PC4 should be able to communicate with SRV2, but the traffic won't succeed since it will always be dropped by R1's G0/2 interface due to inbound ACL rules. The ACL we set is **too restrictive**. PC3 and PC4 can communicate with each other, but that's it.

![Pasted image 20260704214654.png](../_assets/Pasted%20image%2020260704214654.png)

The best interface to place the ACL to fit the requirements is **outbound** on R2's G0/1 interface. PC3's traffic will be denied before it exits the ACL-applied interface, but PC1's traffic will be permitted based on ACL rules. This will also allow PC3 and PC4 to still be able to access SRV2.

Now you get the basic understanding of importance of choosing which router and interface to place ACL to, and the importance of choosing whether it should be inbound or outbound.

**ACL Continuation...**

* ACLs are made up of one or more ACEs.

* When the router checks a packet against the ACL, it processes the ACEs in order, from top to bottom.

* If the packet matches one of the ACEs in the ACL, the router takes action and stops processing the ACL. All entries below the matching entry will be ignored.
  
  ![ 500](../_assets/Pasted%20image%2020260704215249.png)
  ![ 500](../_assets/Pasted%20image%2020260704215351.png)

* A maximum of one ACL can be applied to a single interface <u>per direction</u>.
  **Inbound**: Maximum one ACL
  **Outbound**: Maximum one ACL
  
  This makes the maximum number of ACLs an interface can have is 2: 1 for inbound and 1 for outbound.

* If you create another inbound ACL but there is already a configured inbound ACL, the new ACL will proceed and overwrite the previous inbound ACL. The same is true when creating new outbound ACL but there is already existing outbound ACL: it will overwrite the previous outbound ACL.

### Implicit `deny`

![Pasted image 20260704215846.png](../_assets/Pasted%20image%2020260704215846.png)

* What will happen if a packet doesn't match any of the entries in an ACL?
* There is an **'implicit deny'** at the end of all ACLs.
* The implicit deny tells the router to deny all traffic that doesn't match any of the configured entries in the ACL.
* With implicit deny, the ACL actually has these instructions:
  ![Pasted image 20260704220044.png](../_assets/Pasted%20image%2020260704220044.png)
* Be aware of the presence of implicit deny, as you might deny traffic from hosts by not explicitly mentioning to permit them in the ACL.

### ACL Types

1. **Standard ACLs**: Match based on **Source IP address** <u>only</u>.
   - Standard Numbered ACLs
   - Standard Named ACLs
1. **Extended ACLs**: Match based on **Source/Destination IP, Source/Destination port**, etc.
   - Extended Numbered ACLs
   - Extended Named ACLs

### Standard Numbered ACLs

* Standard ACLs match traffic based only on the source IP address of the packet.

* Numbered ACLs are identified with a number (ie. ACL 1, ACL 2, etc)

* Different types of ACLs have a different range of numbers that can be used.
  - Standard ACLs can use 1-99 and 1300-1999.
  - Below is the list of different ACLs and their range of numbers. There is no need to memorize them for now and just focus on range of numbers for Standard ACLs (Standard IP).
  - ![ 300](../_assets/Pasted%20image%2020260705070351.png)
  - ![ 300](../_assets/Pasted%20image%2020260705070417.png)

* The basic command to configure a standard numbered ACL is:
  **`R1(config)# access-list *number* {deny | permit} *ip* *wildcard-mask*`**
  
  EXAMPLE/s:
  - **`R1(config)# access-list 1 deny 1.1.1.1 0.0.0.0`** -->  Denies `1.1.1.1/32`(a single host)
  - **`R1(config)# access-list 1 deny 1.1.1.1`** --> Denies `1.1.1.1/32` (a single host). If you don't specify the wildcard mask, it defaults to `0.0.0.0` wildcard mask or `/32` prefix length.
  - **`R1(config)# access-list 1 deny host 1.1.1.1`** --> Denies `1.1.1.1/32` (a single host). Same as the previous commands above, but is more of an old method. You can use `host` keyword to specify a single host.
  - **`R1(config)# access-list 1 permit any`** - Permits all hosts. Use this at the end when configuring ACLs as a wildcard otherwise all other hosts not mentioned in ACL would be denied because of **implicit deny**.
  - **`R1(config)# access-list 1 permit 0.0.0.0 255.255.255.255`** - Same as `R1(config)# access-list 1 permit any`, just longer version.
  - **`R1(config)# access-list 1 remark ## BLOCK BOB FROM ACCOUNTING ##`** - This is just like `interface description`. It doesn't do have any effects to ACL but will help with understanding the purpose of the ACL when looking at it from the configuration.

![ 500](../_assets/Pasted%20image%2020260705072208.png)

* After configuring access lists, you can view the configured ACLs with the command **`show access-lists`**.
* When you use /32 mask, the router does not explicitly include what mask is used like what you see in the above output (`10 deny 1.1.1.1`)
* `permit 0.0.0.0 255.255.255.255` was automatically converted to **`permit any`** in `show access-lists` command.
* The remark isn't displayed in `show access-lists` command, but it is displayed in the config.
* Each entries is given a number (10 for `deny 1.1.1.1`, 20 for `permit any`). THIS IS IMPORTANT because the number indicates **order**. If `permit any` comes first before `deny 1.1.1.1`, the host `1.1.1.1` will always be permitted because the next order of execution is ignored after passing the criteria.

![ 500](../_assets/Pasted%20image%2020260705072824.png)

* **`show ip access-lists`** displays all **IP ACLs**. The output is the same as above because we only configured IP ACLs, but `show access-lists` displays all kinds of ACLs.

![ 500](../_assets/Pasted%20image%2020260705073044.png)

* The command above views the access list configured in running configuration.
* We used pipes (`|`) and `include` keyword to only look at configured ACLs.
* This time, the description is shown (`## BLOCK BOB FROM ACCOUNTING ##`).

Remember, ***configuring ACLs doesn't automatically trigger the ACL in a router, you have to enable them in interfaces first to take effect using inbound or outbound***.

### Standard Named ACLs

* Standard ACLs match traffic based only on the source IP address of the packet.

* Named ACLs are identified with a name (ie. 'BLOCK_BOB')

* Standard named ACLs are configured by entering 'standard named ACL config mode', and then configuring each entry within that config mode.
  **`R1(config)# ip access-list standard *acl-name*`**
  **`R1(config-std-nacl)# [entry-number] {deny | permit} *ip* *wildcard-mask*`**

* This improves the efficiency of processing the ACL.
* It **does not** change the effect of the ACL.
* This applies to both standard named and standard numbered ACLs.
* Packet Tracer does not do this, however. So you will see them in order in the way you configured them in order.
